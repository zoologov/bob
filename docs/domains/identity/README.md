# Модуль identity — «кем Боб представляется GitHub'у»

Боб выступает на GitHub **собой**, а не от имени owner'а: у него две учётные сущности
(GitHub App), короткоживущие токены и ровно те права, которые ему выданы. Модуль отвечает
на два вопроса и ни на один сверх них: **кто такой Боб для GitHub** (какой принципал
обслуживает эту операцию) и **чем он аутентифицируется** (App-JWT RS256 →
installation-токен, обновляемый заранее).

Неприкосновенность ствола owner'а здесь перестаёт зависеть от суждения модели: у
принципала, которым Боб работает, нет права записи в апстрим — это свойство выданных
прав, а не аккуратности кода.

**Почему это отдельный bounded context (BOB-089, срез B).** Токены родились как задача
внутри «Боб пишет код», но это другой словарь и другой источник правды:

| | гейтед-кодер (`coding`) | идентичность (`identity`) |
|---|---|---|
| словарь | план, апрув, ветка, PR | принципал, установка, App-JWT, срок токена |
| источник правды | состояние сессии кодера | права, выданные GitHub'ом |
| главный инвариант | `main` только через PR | секрет не попадает ни в argv, ни в лог, ни в текст ошибки |
| что ломается при ошибке | сессия не доехала | Боб выступает не тем, кем должен |

🔴 Пакет — **сосед** (`src/bob/identity/`), а не подпапка `src/bob/coding/`, и это несущее
решение (тот же довод, что у [`interactive`](../interactive/README.md) в BOB-087.E):
beadloom считает размер узла по **префиксу** `source`
(`code_symbols.file_path LIKE '<source>%'`), поэтому вложенный узел учитывался бы дважды и
`coding` (188 символов из 200 на входе в срез) не потерял бы ни одного — разделение было бы
косметическим. Решение координатора при выдаче среза: бюджет не поднимать, узел не
переклассифицировать.

🔴 **Циклов с `coding` нет.** `identity` не импортит из `coding` ничего (только stdlib,
`aiohttp` и `bob.kernel.ports.Clock`); потребитель токена — изоляция окружения спавна
(срез C) — получает провайдер **на композиции**.

## Спецификация

### Раскладка модуля

```
src/bob/identity/
  __init__.py            # layer=domain          — фасад (принципалы, реквизиты, годность токена)
  ports.py               # layer=domain          — Rs256Signer / GitHubAppApi / InstallationTokenSource + семейство отказов
  principals.py          # layer=domain          — Purpose → Principal: назначение операции выбирает права
  credentials.py         # layer=domain          — AppCredentials + разбор секции конфига github с проверкой формы
  app_jwt.py             # layer=domain          — claims App-JWT (RS256), байты для подписи, сборка токена
  token_lifetime.py      # layer=domain          — InstallationToken (repr без секрета) + вердикт «годен / пора обновить»
  adapters/              # layer=infrastructure
    openssl_signer.py    — OpensslRs256Signer: подпись настоящим `openssl dgst -sha256 -sign` (ключ ПУТЁМ, данные в stdin)
    github_api.py        — AiohttpGitHubAppApi: две ручки GitHub App API (секрет только в заголовке)
    installation_token.py — GitHubInstallationTokens: кэш токена на принципала + обновление ЗАРАНЕЕ
```

### Два принципала — потому что права App неделимы

Права GitHub App одинаковы для **всех** его установок: сузить их «для этого репозитория»
нельзя. Отсюда две учётные сущности с разными правами:

- **`Principal.WORK`** («Bob AI Work», `contents: write`, установлен только на организацию
  с приватным форком) — этим принципалом Боб пушит свою ветку. Записать что-либо в апстрим
  owner'а он физически не может: установки там нет.
- **`Principal.PROPOSE`** («Bob AI Propose», `contents: read` + `pull_requests: write`) —
  этим принципалом читается апстрим. Негативный смоук owner'а: создание ветки, force-push
  в `main` и запись файла в апстрим — все три `403 Resource not accessible by
  integration`.

Выбор делает **назначение операции**, а не вызывающий: `principal_for(Purpose.PUSH_TO_FORK)
→ WORK`, всё остальное — `PROPOSE`, то есть принципал без права записи контента. Новое
назначение по умолчанию получает слабейшие права, пока его не разберут в ядре явно.

### Как получается токен

Аутентификация GitHub App двухшаговая, и оба шага живут в модуле:

1. **App-JWT (RS256).** `jwt_claims` собирает ровно три claim'а — `iss` (числовой
   `app_id`), `iat`, `exp`. 🔴 `iat` намеренно сдвинут назад на `CLOCK_DRIFT_SECONDS`
   (60 с): GitHub мерит время по своим часам и отвергает `iat` из будущего. Сумма сдвига и
   времени жизни проверяется против `MAX_JWT_SPAN_SECONDS` (600 с — предел GitHub) **на
   сборке**: ронять здесь дешевле, чем ловить невнятный `401` из сети. `signing_input`
   отдаёт байты `base64url(header).base64url(claims)` (компактный JSON с сортированными
   ключами — те же claims дают те же байты), `assemble_jwt` приклеивает подпись; пустая
   подпись отвергается.
2. **Installation-токен.** `GET /repos/{owner}/{repo}/installation` находит установку
   принципала (токен GitHub скоупится на **одну** установку, поэтому установка ищется по
   обслуживаемому репозиторию, а не берётся «первой из списка»), затем
   `POST /app/installations/{id}/access_tokens` выдаёт сам токен и его срок. Установка
   ищется один раз за жизнь провайдера, токен — по мере надобности.

**Без новых зависимостей.** PyJWT и `cryptography` в проекте нет, и тянуть их ради одной
подписи — плата всей поверхностью транзитивных зависимостей в самом чувствительном месте.
Подпись делает `openssl dgst -sha256 -sign` (тот же путь, которым координатор подписывал
JWT вживую при настройке доступов), а HTTP — уже имеющийся `aiohttp`.

### 🔴 Обновление ЗАРАНЕЕ, а не по факту 401

Installation-токен живёт час, а сессия кодера бывает длиннее. Дожидаться отказа означало бы
ронять работу в середине: часть сделана, ветка не запушена, а вызывающему приходит невнятная
ошибка прав. Поэтому вердикт `token_freshness` объявляет токен негодным **за
`token_margin_seconds` до конца** (по умолчанию 300 с — заметно больше самой долгой
git-операции): лишний минт стоит одного запроса, потерянная сессия — несравнимо дороже.

Смежные решения того же ядра: токена нет → `RENEW` (первый вызов — не ошибка);
отрицательный запас — не настройка, а опечатка, и он отвергается; **сломанный срок
всплывает, а не угадывается** — ответ без `expires_at` или с наивным временем даёт
`TokenMintError` (урок BOB-087.E1: контрактный сбой нельзя маскировать; токен с неизвестным
сроком невозможно обновить заранее, значит нельзя и пользоваться им молча).

Одновременные запросы одного принципала дают **один** минт: годность перепроверяется под
замком принципала. Кэши двух принципалов независимы — один кэш на двоих означал бы работу
чужим токеном.

### 🔴 Где секрет живёт, а где его не бывает

Это главный инвариант модуля, и он держится структурно, а не обещанием:

- **argv.** Приватный ключ передаётся **путём** (`.secrets/*.pem`, 0600), подписываемые
  байты уходят в **stdin**. Содержимое ключа в командной строке было бы видно в `ps` любому
  процессу пользователя. PEM, случайно вставленный в конфиг вместо пути, отвергается — и
  сам секрет в текст отказа не попадает.
- **Заголовок, а не командная строка.** Запрос к `api.github.com` делается in-process через
  `aiohttp` именно поэтому: `curl` унёс бы `Authorization: Bearer <JWT>` в argv.
- **Лог.** В отладочный лог идут принципал, `app_id` и срок жизни — по ним видно, кто ходил
  за токеном и когда пойдёт снова. Ни JWT, ни значение токена там не появляются.
- **Текст ошибки.** Диагностика по **типу** отказа (`IdentityConfigError` — настроено не
  так; `SigningError` — не подписали; `TokenMintError` — GitHub не выдал или ответил не тем)
  плюс шаг, HTTP-статус, `app_id`, путь к ключу. Тело ответа GitHub в диагностику не
  вкладывается (там бывает эхо запроса), stderr `openssl` — тоже.
- **`repr`.** У `InstallationToken` своё представление: срок виден, значение — `<redacted>`.
  `repr` уезжает в traceback и в отладочный лог, где секрет осел бы навсегда.

### Конфигурация (секция `github`, всё пусто по умолчанию)

| Ключ | Что это |
|---|---|
| `work_app_id` / `propose_app_id` | числовой `app_id` GitHub App (claim `iss`) |
| `work_app_key` / `propose_app_key` | 🔴 **путь** к приватному ключу, никогда его содержимое |
| `work_repo` / `propose_repo` | `owner/repo`, по которому находится установка принципала |
| `token_margin_seconds` | запас обновления заранее (300) |
| `jwt_lifetime_seconds` | время жизни App-JWT (480, внутри предела GitHub) |
| `api_base_url` / `openssl_bin` / `timeout_seconds` | шов транспорта и подписи |

Значения приезжают из `.env` (`BOB_GITHUB__WORK_APP_ID`, `BOB_GITHUB__WORK_APP_KEY`, …), а
не из репозитория. Пустая секция означает «Боб не настроен»: сборка провайдера
(`build_installation_tokens`) при этом **не падает**, а отказ приходит с именем недостающего
ключа в тот момент, когда токен реально понадобился. Реквизиты разбираются лениво, по
принципалу: ненастроенный `propose` не лишает Боба его рабочего принципала.

### Публичная поверхность

- `principals.py`: `Purpose{PUSH_TO_FORK, READ_UPSTREAM}`, `Principal{WORK, PROPOSE}`,
  `principal_for(purpose)`.
- `credentials.py`: `AppCredentials(app_id, private_key_path, repository)`,
  `credentials_for(section, principal)`.
- `app_jwt.py`: `jwt_claims(*, app_id, now, lifetime_seconds)`, `signing_input(claims)`,
  `assemble_jwt(payload, signature)`, `b64url(raw)`, `CLOCK_DRIFT_SECONDS`,
  `MAX_JWT_SPAN_SECONDS`.
- `token_lifetime.py`: `InstallationToken(value, expires_at)`, `Freshness{USABLE, RENEW}`,
  `token_freshness(*, expires_at, now, margin_seconds)`, `parse_expiry(raw)`.
- `ports.py`: `Rs256Signer`, `GitHubAppApi`, `InstallationTokenSource`; отказы
  `IdentityError` → `IdentityConfigError` / `SigningError` / `TokenMintError`.
- `adapters/`: `OpensslRs256Signer(openssl_bin=…, timeout_seconds=…)`,
  `AiohttpGitHubAppApi(base_url=…, timeout_seconds=…, request=None)`,
  `GitHubInstallationTokens(section, *, signer, api, clock, renew_margin_seconds,
  jwt_lifetime_seconds)`, `build_installation_tokens(section, *, clock)`.

## Честная рамка среза B

- Модуль **выдаёт** токены; изоляции окружения спавна (credential helper Боба вместо
  helper'а owner'а) в нём нет — это срез C, и до него токен ни одним прод-путём не
  запрашивается. То есть сейчас это фундамент с доказанным поведением, а не включённая
  фича: провайдер собирается, но вызывающего в проде у него пока нет (правило §0.3 п.10 —
  «разрешение без вызывающего не возможность» — здесь соблюдено сознательно и записано).
- Боб **не может** сам открыть PR из приватного форка: installation-токен скоупится на одну
  установку, а cross-repo PR требует читаемости обеих сторон одним токеном (проверено три
  способа, см. комментарии беады BOB-089). Вариант A: Боб доводит работу до ветки в форке и
  отдаёт owner'у ссылку.

## Тесты

- **Чистые ядра** — `tests/domain/identity/test_principals.py`, `test_credentials.py`,
  `test_app_jwt.py`, `test_token_lifetime.py`. Это mutation-цели
  (`./scripts/mutation.sh identity.app_jwt` и так далее); пакет внесён в
  `[tool.mutmut].source_paths`, иначе гейт этих ядер был бы фантомным (§0.3 п.7).
- 🔴 **Настоящий openssl** — `tests/infrastructure/identity/test_openssl_signer_real_openssl.py`:
  тест генерирует настоящую RSA-пару в одноразовом каталоге (не в `.secrets/`), подписывает
  реальным `openssl dgst -sha256 -sign` и **проверяет подпись обратным**
  `openssl dgst -sha256 -verify` — вердикт даёт сам openssl. Подмена одного байта подписи
  проверку роняет (контроль на вакуумность), подпись чужого payload'а не проходит, а
  перехват сборки argv доказывает, что ключевой материал в командную строку не попадает.
  Фейк здесь доказал бы контракт фейка (§0.3 п.4).
- **Адаптеры** — `tests/infrastructure/identity/test_github_api.py` (куда уходит запрос, что
  в заголовке, как всплывает сломанный ответ — на детерминированном шве, без живой сети),
  `test_installation_token.py` (кэш, обновление заранее, два принципала, один минт при
  гонке, отсутствие секретов в логе и в отказах; 🔴 фейки транспорта НАМЕРЕННО уступают
  управление циклу — без точки приостановки тест на гонку проверял бы контракт фейка, что и
  вскрылось проверкой на кусачесть), `test_build_installation_tokens.py` (сборка из конфига
  не падает на ненастроенном Бобе; настройки пробрасываются, мусорное значение не
  превращается в нулевой запас).
- 🔴 **Живой смоук** — `tests/infrastructure/identity/test_github_live_smoke.py`:
  READ-ONLY `GET /repos/{repo}/installation` против настоящего GitHub, **opt-in** по
  `BOB_LIVE_GITHUB_SMOKE=1` (иначе пропуск с явной причиной, сеть не трогается). openssl
  подтверждает, что подпись верна математически; принимает ли её САМ GitHub — вопрос его
  верификатора. Прогон вживую в срезе B: приняты оба принципала, установки разные (`work` —
  на форке, `propose` — на апстриме).
- **Конфиг** — `tests/test_github_identity_config.py`: секция ship'ится пустой, ключи
  из `.env` доезжают, в дефолтах нет ничего похожего на секрет.

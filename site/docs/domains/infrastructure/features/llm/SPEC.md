# llm — адаптер LLM (OpenAI-совместимый провайдер)

Адаптер инфраструктуры для LLM: OpenAI-совместимый провайдер завершений Tier 0/1 и
tool-calling поверх aiohttp (backend — Ollama/Qwen). Узел `llm` (`part_of` слоя
`bob-infrastructure`, source `src/bob/infrastructure/llm/`) реализует порт `LLMProvider`
из kernel; вся редакция приватности и маршрутизация тиров живут выше, в узле `router`.
Здесь же живёт аварийный фолбэк Tier 0 на локальную модель — по умолчанию выключенный.

## Спецификация

### Модули

- **openai_compat.py** — `OpenAICompatProvider`, OpenAI-совместимый провайдер
  chat-completions поверх aiohttp: `complete(...)` (обычное завершение, опционально
  стриминг токенов) и `complete_with_tools(...)` (нативный tool-calling ход для tool-loop'а).
- **factory.py** — сборка провайдеров из конфигурации:
  - `build_tier_providers(...)` — построить провайдеры Tier 0 (быстрый) и Tier 1
    (качественный); при `llm.tier0_fallback` = `ollama` Tier 0 отдаётся завёрнутым в
    композит с локальным дублёром (пусто — по умолчанию — ровно тот же провайдер,
    что и раньше).
  - `build_web_search_provider(...)` — построить провайдер веб-поиска.
- Вердикт «это авария связи или наш дефект» живёт **не здесь**: чистое ядро
  `should_fall_back(error)` переехало в `src/bob/application/router/fallback_policy.py`
  (bob-41o), потому что тем же вердиктом судит верхний фолбэк роутера Tier1 → Tier0, а
  правило `application-no-infra` запрещает слою application тянуться в infrastructure.
  Композит ниже импортит его вниз по слоям. Классификация описана в разделе «Что
  считается поводом уйти на более слабую модель».
- **fallback_provider.py** (BOB-087.E1, .E1b) — композит primary + локальный аварийный
  fallback, реализующий тот же порт `LLMProvider`: `FallbackLLMProvider` (только
  `complete`) и `ToolCallingFallbackLLMProvider` (плюс `complete_with_tools` под той же
  политикой). Какой из двух собрать — решает `build_fallback_provider(...)` по
  способностям primary.
- **__init__.py** — фасад пакета (OpenAI-совместимый провайдер + Tier 0/1 провайдеры).

### Аварийный Tier-0-фолбэк (BOB-087.E)

Оба тира в боевой конфигурации указывают на облако Qwen/Aliyun: имя внутренней
константы `_TIER_LOCAL` историческое, локальным Tier 0 давно не является. Облако
периодически пропадает из сети (в BOB-084 наблюдалось 77 отказов подряд), а
запасного пути у нулевого тира нет — вместе с ним отваливаются классификаторы,
внутренний монолог и гейты кодера. Фолбэк даёт Tier 0 локального дублёра: модель
Ollama на той же машине.

| Ключ секции `llm` | По умолчанию | Смысл |
|---|---|---|
| `tier0_fallback` | `""` — выключено | имя локального backend'а. Поддерживается только `ollama`; любое другое значение — `KeyError` при сборке |
| `tier0_fallback_base_url` | `http://localhost:11434/v1` | OpenAI-совместимая поверхность Ollama (отсюда суффикс `/v1` — секции `embeddings` и `reranker` смотрят на голый хост, потому что их адаптеры дописывают путь сами) |
| `tier0_fallback_model` | `qwen2.5:0.5b` | модель дублёра |

Поставляется выключенным. Пока `tier0_fallback` пуст или ключа нет вовсе,
`build_tier_providers` отдаёт на Tier 0 тот же самый `OpenAICompatProvider`, что и до
среза, — ни одна новая ветка не исполняется. Включение — `BOB_LLM__TIER0_FALLBACK=ollama`;
это аварийный режим, а не второй основной тир (см. «Известные ограничения»).

Дублёр наследует настройки вызова Tier 0 — таймаут, `disable_thinking`, температуру, —
чтобы деградировавший ход отвечал как Tier 0, а не как третий, иначе настроенный тир.
Ключ API ему не передаётся: он локальный.

Ход при включённом фолбэке: одна попытка на облаке, и, если сбой признан транспортным,
одна попытка на локальной модели. Каскадов и повторов нет. Легли обе — наружу уходит
исходная ошибка облака (она объясняет, с чего всё началось), отказ локальной модели
прицеплен к ней как `__cause__`. У потокового хода фолбэка нет вовсе, он делегируется
primary напрямую: сбой стрима всплывает посреди итерации, когда часть токенов уже
прочитана, и повтор дублировал бы вывод, а не спасал ход. Tier 0 сегодня никто не стримит.

Что видит владелец: каждое переключение — строка `WARNING` в логе (`./bob logs`) с типом
и текстом причины и с указанием, какой ход деградировал — обычный чат или tool-ход
(у маленькой модели просадка на инструментах резче, чем на разговоре). Если легла и
локальная модель, пишется второй `WARNING`. На здоровом ходе лог молчит.

### Что считается поводом уйти на более слабую модель

Вердикт выносит чистое ядро `should_fall_back(error)` (`bob.application.router.fallback_policy`),
общее для ОБОИХ этажей тиринга: и для этого композита (облачный Tier-0 → локальный дублёр),
и для фолбэка роутера Tier1 → Tier0 (bob-41o). Одна политика, а не две расходящиеся. Граница проходит между сбоем
**канала** и сбоем **контракта**, и это главное решение среза: фолбэк, срабатывающий на
нашем собственном дефекте, устойчивости не добавляет — он прячет дефект за тихо
деградировавшим ответом. Кривой запрос, протухший ключ, несуществующая модель обязаны
быть видны как отказ, а не молча обслуживаться другой моделью.

**Уходим — эндпоинт не смог нас обслужить:** таймаут (`TimeoutError`); отказ соединения,
сброс, ошибка DNS (`OSError` и родня, `aiohttp.ClientConnectionError`); обрыв на полуслове
(`ServerDisconnectedError`) и оборванное тело ответа (`ClientPayloadError`); HTTP 5xx;
HTTP 408 (эндпоинт сам не дождался) и 429 (облако сейчас нас не обслуживает — с нашей
стороны это недоступность).

**Не уходим — это контракт, его надо показать:** прочие 4xx (400, 401, 403, 404, 409,
413, 422) — наш кривой запрос, ключ или модель; битая форма ответа (`ValueError` из
парсеров, `json.JSONDecodeError`) — вызов удался, содержимое неверно; `aiohttp.InvalidURL`
как дефект конфигурации, а не сетевое событие; голый `aiohttp.ClientError` без
транспортных улик; `TypeError`, `RuntimeError` и прочие программные ошибки; отмена
(`asyncio.CancelledError`) и `KeyboardInterrupt` — остановка процесса обязана пролетать
мгновенно, а не «ретраиться» на локальной модели.

Осмысленный отказ модели и пустой, но валидный ответ до политики не доходят вовсе:
`openai_compat` деградирует отсутствующее содержимое до пустой строки и исключение не
бросает. Фолбэк существует только ради аварий.

## Инварианты

- `OpenAICompatProvider` реализует контракт `LLMProvider` (kernel) структурно —
  приложение зависит от порта, а не от этого конкретного адаптера.
- Сетевой ввод-вывод изолирован в этом адаптере; домен и use-case'ы к aiohttp не касаются.
- `complete_with_tools` несёт богаче-типизированные `ToolLoopMessage` (структурный
  `tool_calls`); обычный `complete` остаётся string-only.
- Аварийный Tier-0-фолбэк никогда не каскадит: одна попытка primary → одна попытка
  локальной модели; упали обе — наружу уходит исходная ошибка primary. Каждое
  переключение логируется `WARNING` (тихая деградация недопустима).
- Композит — единственное место, где живёт МЕХАНИКА нижнего фолбэка: маршрутизация тиров
  в `LLMRouter` от него не зависит. ПОЛИТИКУ («что считать аварией») оба этажа с bob-41o
  берут из общего ядра `bob.application.router.fallback_policy`, поэтому строгость нижнего этажа
  не может разойтись со строгостью верхнего.
- Обёртка не меняет способности завёрнутого тира (BOB-087.E1b): композит объявляет
  `complete_with_tools` ровно тогда, когда его умеет primary — ни меньше (шов
  tool-loop'а проверяет через `hasattr`, потеря была бы БЕЗМОЛВНОЙ), ни больше
  (ложное объявление подсунуло бы шву провайдера, который не отработает).
- Локальная модель подменяет tool-ход только если объявляет `complete_with_tools`: ответ
  без запрошенных инструментов — не «ухудшенный», а другой, и tool-loop этого не отличит.
  Проверка структурная, её пределы описаны в «Известных ограничениях».
- Выключенный флаг возвращает прежнюю сборку буквально: на Tier 0 стоит тот же класс с
  тем же состоянием, что и до среза, — не «примерно то же самое» (закреплено тестами
  фабрики, отдельно для пустого значения и для отсутствующего ключа).

## Известные ограничения

🔴 **Локальный дублёр отвечает не только служебным ходам — он отвечает и в чат.**
Tier 0 обслуживает не только классификаторы, монолог и гейты кодера: короткую
casual-реплику `HandleMessage` тоже отправляет на нулевой тир — `select_reply_tier`
выбирает Tier 0 для всего, что не выглядит сложным: короткий текст без блока кода, без
нескольких вопросов подряд и без «глубоких» ключевых слов. Значит при включённом флаге
и отвале облака ответ владельцу или
группе сгенерирует локальная модель: по умолчанию `qwen2.5:0.5b` против боевого
`qwen3.6-flash` на Tier 0. Композит по построению невидим вызывающему — он возвращает
обычную строку, поэтому `HandleMessage` не может ни пометить такой ход, ни воздержаться от
его записи, и реплика ложится в нить и в `episodic_log` как обычный голос Боба. Дальше она
становится материалом для recall и продолжает влиять на тон уже после того, как облако
вернулось (проект наступал на это в BOB-022, BOB-074 и BOB-078). То есть у аварийного
режима есть последствие, которое переживает саму аварию. Ограничение найдено ревью среза
E3; решение по нему владелец ещё не принял, поэтому `llm.tier0_fallback` остаётся
выключенным.

**Локальная модель не равноценна облачной.** Дублёр нужен, чтобы ход завершился, а не
чтобы он завершился так же хорошо. Неуязвимым к отвалу облака фолбэк Боба не делает —
он лишь даёт ходу шанс дойти до конца на слабой модели.

**Проверка «локальная модель умеет tool-calling» — структурная.** `ToolCallingProvider` —
`runtime_checkable`-протокол, то есть `isinstance` подтверждает лишь наличие метода
`complete_with_tools`. В собранной поставке дублёр — тот же `OpenAICompatProvider`, у
которого метод есть всегда, поэтому ветка «локальная не умеет инструменты, сбой уходит
наружу» в реальной конфигурации недостижима. Она ловит подставной адаптер без метода, но
не неспособность конкретной маленькой модели вызывать инструменты — считать её работающей
защитой нельзя.

**Дублёр наследует общий `timeout_seconds`** (в боевой конфигурации 180 секунд). На форме
отказа «облако приняло запрос и молчит» ход стоит два ожидания подряд. Большинство реальных
отказов — отказ соединения и сброс — падают быстро, поэтому средняя цена невелика, но
отдельного короткого бюджета у дублёра нет.

**`OSError` — широкая корзина.** В неё попадает и `ssl.SSLError`, поэтому протухший или
подменённый сертификат облака классифицируется как «облако легло» и уводит ход на локальную
модель. Утечки при этом нет — в подозрительный эндпоинт мы как раз не идём, а тип ошибки
виден в `WARNING`. Симметрично 429 поглощает и наш собственный runaway (прецедент BOB-076).
Оба огрубления приняты сознательно.

**Состояния деградации нет, сигнал поштучный.** Логируется каждое переключение, но переходы
«здоров → деградировал» и обратно отдельно не отмечаются, и `./bob status` о режиме ничего
не знает. При затяжной аварии в логе окажутся сотни одинаковых строк, из которых не
прочитать главного: живёт ли Боб на аварийной модели прямо сейчас.

**«Локальность» дублёра держится на значении по умолчанию.** `tier0_fallback_base_url`
берётся из конфигурации как есть, проверки на loopback нет: чужой хост в этом ключе увёл бы
туда весь Tier-0-материал, включая приватный контекст. Смягчено тем, что дублёр строится
без ключа API и посторонний endpoint нас, скорее всего, отвергнет.

## API

Модуль `src/bob/infrastructure/llm/openai_compat.py`:
- `OpenAICompatProvider.complete(messages, *, stream=False)` → завершение чат-хода.
- `OpenAICompatProvider.complete_with_tools(...)` → нативный tool-calling ход.

Модуль `src/bob/infrastructure/llm/factory.py`:
- `build_tier_providers(...)` → провайдеры Tier 0 / Tier 1.
- `build_web_search_provider(...)` → провайдер веб-поиска.

Модуль `src/bob/infrastructure/llm/fallback_provider.py`:
- `build_fallback_provider(primary=…, fallback=…)` → композит, зеркалящий способности
  primary (единственный поддерживаемый способ сборки).
- `FallbackLLMProvider(primary=…, fallback=…).complete(messages, *, stream=False)` →
  завершение на primary, при транспортном сбое — одна попытка на локальной модели.
- `ToolCallingFallbackLLMProvider(primary=…, fallback=…)` → композит для tool-calling
  primary; без такого primary конструктор бросает `TypeError`, чтобы объект не объявил
  способности, которой у него нет.
- `ToolCallingFallbackLLMProvider.complete_with_tools(messages, *, tools)` → tool-ход на
  primary, при транспортном сбое — одна попытка на локальной модели (только если та
  объявляет `complete_with_tools`; иначе наружу уходит исходный сбой primary).

Конфиг секции `llm`: `tier0_fallback`, `tier0_fallback_base_url`, `tier0_fallback_model` —
значения и смысл в разделе «Аварийный Tier-0-фолбэк».

# Модуль presence — «живой ритм Боба»

Ритм-слой «человеческого группового присутствия» (BOB-066) как единая вертикаль
чистой доменной логики: насколько Боб занимает эфир (доля голоса), как быстро он
по-человечески отвечает (естественная задержка), как экономно ставит лайки
(бюджет реакций) и как по-человечески догоняет накопившийся за отсутствие бэклог
(один проход под бюджетом вместо очереди ответов на каждое пропущенное сообщение).
Это про **ритм равного участника**, а не про то, ЧТО он говорит
(вердикт — в `conversation`) и не про его фоновую тягу заговорить первым (drive —
в `proactivity`). Все политики чистые: без I/O, без часов, без rng — время и
случайность инъектятся вызывающей стороной, поэтому вердикты детерминированы и
проверяются без LLM.

Это новый **вертикальный** bounded-context (срез BOB-066.2.3): бизнес-логика
ритма собрана в `src/bob/presence/`, а не размазана по слоям. Модуль охватывает
domain + adapters **внутри** одного контекста, поэтому в графе несёт не-слойный тег
`module-vertical` (правило `architecture-layers` его рёбра пропускает), а
внутреннюю и внешнюю дисциплину держат сгенерированные path-glob
`forbid_import`-правила в `.beadloom/_graph/rules.yml`
(`python scripts/gen_boundary_rules.py`).

## 🔴 Решение по принадлежности — отдельный контекст, не в proactivity

Доля эфира / естественная задержка / бюджет реакций **сознательно вынесены в
отдельный `presence/`**, а не сложены в `proactivity/`. Проактивность — это
*тяга заговорить первым* (urge из настроения/тоски/свежести рефлексии); presence —
это *ритм живого участника* уже идущего разговора. Разные ответственности → разные
контексты (когезия). Оба, впрочем, читают одно и то же окно активности per-chat:
проактив-тик может домножать своё окно на ту же долю голоса, чтобы не заговорить
поверх только что отправленной реплики.

## 🔴 Провязка за флагами `presence.*` (OFF по умолчанию)

Эпик BOB-066 — блокер owner'а: команда в группу добавляется, только когда всё
готово ЦЕЛИКОМ. Поэтому вся **поведение-меняющая** провязка presence-слоя идёт за
нестед-фичефлагами `presence.<section>.enabled`, выключенными по умолчанию
(консистентно с `presence.reflective` из среза 2.2). Срез W провязал потребление
всех механизмов в горячий путь через коллабораторов — но builder'ы
(`runtime/wiring/*.py`) возвращают `None`/inert-bundle, пока флаг выключен, поэтому
продакшн-путь ответа байт-в-байт равен пред-BOB-066:

- `presence.rhythm.enabled` — soft-ceiling доли эфира (`ShareOfVoiceGate` →
  `barge_ceiling`/`share_ceiling`) + человеческий пол задержки (`DelayedTurn`, INV-9);
- `presence.staleness.enabled` — врезка переоценки черновика перед отправкой
  (`StalenessReassessor`);
- `presence.catchup.enabled` — догоняющий проход в per-chat воркере (`CatchUpReentry`);
- `presence.series_budget.enabled` — batch top-k бюджет действий (`plan_series_actions`);
- `presence.stream_read` — 🔴 голый bool (НЕ `.enabled`): холистический stream-read
  ambient-пачки (BOB-072) вместо скриптованного top-k; включает окно коалесинга
  `dialogue.intake_debounce_ms` и очередный `coalesce_stale`.

Полный список флагов эпика (включая `presence.room_mood` / `presence.endorsement` /
`presence.tact` из соседних доменов) с точными путями, формами и knobs — в разделе
«Активация» [`architecture.md`](../../architecture.md#активация-человеческого-группового-присутствия-bob-066).

Application-коллабораторы ритма живут под `src/bob/application/runtime/`
(оркестрация — не домен): `DelayedTurn` (порядок «заметил → typing → await
max(пол, генерация) → reply»), `ShareOfVoiceGate` (потолок на p(ambient-барджа);
фокус минует; rng-draw инъектится из `TurnScope`) и `StalenessReassessor`
(`staleness_reassessor.py` — тонкий коллаборатор над гейтом устаревания: проецирует
`MessageReceived` на доменный `ArrivedMessage`, зовёт судью только когда что-то
прилетело, возвращает исход гейта) и `CatchUp`
(`usecases/catch_up.py` — один догоняющий проход над бэклогом отсутствия: проецирует
`MessageReceived` на доменный `BacklogMessage`, зовёт `select_catchup` под бюджетом
и подмешивает тон входа `absence_hint`).

### Инварианты (структурные гарантии)

- **INV-1 (фокусная гарантия):** `ShareOfVoicePolicy.damping(..., focused=True)`
  всегда `1.0` — прямое обращение потолок НЕ трогает. `ShareOfVoiceGate` пробрасывает
  `focused` в политику.
- **INV-3 (анти-скрипт):** потолок — мягкий вероятностный множитель `> 0` (пол
  `share_min_multiplier`), а решение — случайный draw, а не жёсткий счётчик. Боб
  притормаживается, но не немеет.
- **INV-9 (живой тайминг):** `NaturalDelayPolicy` даёт только ПОЛ; `DelayedTurn`
  ждёт `max(пол, реальная генерация)` — реальная генерация всегда выигрывает, если
  дольше, поэтому Боб никогда не медленнее себя настоящего, только не мгновенный.
- **INV-10 (фокус никогда не теряется в догоняющем проходе):** `select_catchup`
  безусловно кладёт КАЖДОЕ прямо-адресованное (`addressed_to_bob`) сообщение в
  `to_answer`; бюджет режет только не-фокусные слоты. Прямое обращение не может
  оказаться в `collapsed` ни при каком бюджете — на уровне скоринга это держит
  зазор банда (`1.0`) больше максимума внутри банда (`0.6·freshness + 0.3·salience =
  0.9`), поэтому свежесть/salience никогда не перепрыгивают банд.
- **INV-11 (никогда не молчаливый сброс):** гейт устаревания сбрасывает черновик до
  реакции (`DROP_TO_LIKE`) ТОЛЬКО когда реплика стала избыточной. Пустая пачка →
  `SEND` без вызова судьи; недоступный/упавший судья (нет `reading`) → `SEND`
  fail-safe. Боб никогда молчаливо не теряет реплику, которую уже написал.

### Доля эфира (Q3 RFC)

Целевая доля ≈ `1 / (distinct_senders + 1)` — «как ещё один человек в комнате». Пока
доля Боба ≤ цели — множитель `1.0` (барджит свободно); выше — плавно затухает с тем,
насколько он превысил справедливую долю, с полом над нулём. Больше участников →
уже цель → раньше торможение.

### Гейт устаревания черновика (B2 = B7)

Живой участник не выстреливает репликой, которую написал полминуты назад, в
комнату, которая уже ушла вперёд. Пока Боб печатал, могли прилететь другие
сообщения: кто-то другой ответил ровно на его мысль, тред закрылся, спрашивавший
уточнил вопрос или сверху прилетел свежий прямой вопрос. `StalenessGate`
(`staleness.py`) держит ОДНО чистое решение, которое превращает «что прилетело за
время генерации» в исход для черновика:

- **`SEND`** — ничего значимого не сместилось, отправить черновик как есть.
- **`REWRITE`** — тот же автор уточнил/поправил вопрос, перегенерировать.
- **`DROP_TO_LIKE`** — реплика теперь избыточна (ответили за него / тема закрыта),
  поставить реакцию вместо устаревшей строчки.
- **`MERGE`** — прилетел свежий прямой вопрос, свернуть оба в ОДНУ реплику (dedup —
  никогда две реплики на один обмен).

🔴 **B2 = B7 (один примитив).** Переоценка ПОСЛЕ генерации (post-draft) и прерывание
ПОСРЕДИ генерации — один и тот же акт «переоценить черновик под сместившимся
контекстом», поэтому оба идут через этот единственный гейт и один коллаборатор.

По несущему принципу эпика (`LLM вербализует → чистое ядро решает`) семантическое
чтение сдвига вербализует судья (`StalenessReading` через порт `StalenessJudge`), а
чистое детерминированное ядро `decide_staleness(reading)` РЕШАЕТ исход — ровно как
`conversation.room_verdict.decide_from_reading`. Без I/O, без часов, без rng:
вердикт пиннится юнит-тестами и закалён мутационным тестированием (100%).

**Порядок предпочтения (mutation-pinned, INV-1 примирён в Срезе W.3):** свежий прямой
вопрос вперёд всего — `new_direct_question → MERGE` (проверяется ПЕРВЫМ, поэтому прямой
вопрос НИКОГДА не роняется в реакцию); затем избыточность
`answered_by_other | topic_closed → DROP_TO_LIKE`; затем `same_author_clarified →
REWRITE`; иначе `SEND`. Фасад
`StalenessGate.reassess` оборачивает ядро двумя структурными рельсами без вызова
судьи: пустая пачка → `SEND`, отсутствие `reading` (судья недоступен/упал) → `SEND`
fail-safe (см. INV-11).

**Переиспользование буфера intake.** Коллаборатор `StalenessReassessor`
(`application/runtime/staleness_reassessor.py`) НЕ строит второй буфер: пачка
«прилетевшего за генерацию» — это недренирующий снимок
`ChatInbox.peek_since` (буфер приёма из среза 2.1), переданный ВНУТРЬ как
`newly_arrived`. Судья зовётся только когда что-то прилетело. Транспортные признаки
(`reply_to_bob`, `from_draft_author`) выводятся на прикладном шве, который знает
user-id Боба и кому он пишет ответ, поэтому доменный `staleness.py` свободен от
импорта `MessageReceived`.

**Провязка live за флагом `presence.staleness.enabled` (BOB-066 Срез W.3).** Горячая
врезка `handle_message._drop_to_like_if_stale` теперь вшита: перед `gateway.reply`
`StalenessReassessor` перечитывает `scope.peek_arrivals` (turn-local снимок буфера),
зовёт судью и на `DROP_TO_LIKE` роняет черновик в реакцию + пол-нереплай; иначе
(`MERGE`/`SEND`/`REWRITE`) — отправка. Флаг `presence.staleness.enabled` OFF по
умолчанию → `staleness_reassessor` не строится, `peek_arrivals` не биндится, путь
байт-в-байт. Живой Tier-0 судья — `presence/adapters/staleness_judge.py`
(`LlmStalenessJudge`, `TaskType.STALENESS_JUDGE`).
🔴 **INV-1 примирён на уровне ядра:** `decide_staleness` теперь проверяет
`new_direct_question` ПЕРВЫМ (до `answered_by_other`/`topic_closed`), поэтому свежий
прямой вопрос → `MERGE`, а не `DROP_TO_LIKE` — никогда не сбрасывается до реакции (дух
INV-1 «никогда не терять реплику»). Порядок предпочтения обновлён (см. ниже).

### Очередный стейл-коалесинг ambient-пачки (BOB-072, за `presence.stream_read`, OFF)

Перед холистическим stream-read'ом (`conversation`, чтение всей осевшей вспышки одним
Tier-1 read) осевшую ambient-пачку прореживает второе чистое ядро — `coalesce_stale`
(`staleness.py`). Это «оставайся в настоящем» (INV-S3) на уровне ОЧЕРЕДИ, до чтения:
сообщение считается перекрытым, ТОЛЬКО если ТОТ ЖЕ опознанный отправитель говорит снова
в самом следующем слоте вспышки (переспрос/переформулировка, которую поток уже обогнал),
поэтому Боб отвечает на последнюю форму, а не на устаревшую. Правило сознательно
консервативно (liveness > экономия):

- **`QueuedAmbient`** — одно буферизованное ambient-сообщение в примитивах-значениях
  (`sender_id`, `is_focal`), переносится ПО ЗНАЧЕНИЮ, чтобы домен presence не тянул
  импорты application/транспорта.
- **`coalesce_stale(batch) -> tuple[bool, ...]`** — на каждое сообщение решает KEEP
  (`True`) или «перекрыто» (`False`), детерминированно и с mutation-пиннингом.
- 🔴 **Focal никогда не перекрывается** (`is_focal` → всегда KEEP) — примиряет отсев с
  INV-1: прямое обращение — гарантия. Ambient-пачка приходит сюда уже без focal (он
  отделён выше по потоку); флаг — оборонительный рельс, чтобы ядро не уронило focal.
- **Неопознанный** отправитель (`sender_id is None`) не коалесится (две анонимные строки
  не доказуемо «тот же отправитель»); сообщение с **другим отправителем между** повторами
  того же — KEEP (тема могла разветвиться).

Перекрытое сообщение выпадает ТОЛЬКО из чтения — вызывающая сторона всё равно персистит
его и двигает floor (INV-S2): тред цел, Боб просто не отвечает на устаревшую форму.

### Догоняющий проход по бэклогу (Пласт 3 §Догоняющий)

Вернувшись в чат, который заполнился за его отсутствие, живой участник не строчит
ответ на каждое пропущенное сообщение. Он окидывает кучу ОДНИМ взглядом и отвечает
тем немногим, кому действительно нужен, — под бюджетом, — а фоновую болтовню,
которую лишь бегло просмотрел, так и оставляет просмотренной. `catchup.py` держит
две чистые части этого «догоняй по-человечески»:

- **`score(msg, *, now)` — приоритет одного сообщения одним числом.** Порядок
  **банд-лексикографический и несущий**: прямо-адресованное Бобу всегда старше
  ответа в его треде, который всегда старше ambient-болтовни, — как бы свежа или
  интересна ambient ни была. Внутри банда свежесть весит больше salience
  (`0.6·freshness + 0.3·salience`), и их сумма (`≤ 0.9`) по построению меньше зазора
  банда (`1.0`), поэтому банд НИКОГДА не перепрыгивается. `rank` — стабильная
  сортировка по убыванию score (равные держат порядок прилёта: старшие вперёд).
- **`select_catchup(messages, *, now, budget)` — ОДИН рефлексивный проход:**
  ранжирует весь бэклог и оставляет верх под бюджетом действий, возвращая
  `CatchUpPlan(to_answer, collapsed)` — разбиение бэклога (непересекающиеся +
  покрывающие). 🔴 **Бэкпрешер с приоритетом:** фокусное (прямо-адресованное)
  сообщение НИКОГДА не роняется и не схлопывается — бюджет режет только **не-фокусные
  слоты** (INV-1/INV-10). Внутри бюджета не-фокусные конкурируют по банду:
  ответ-в-треде Боба забирает дефицитный слот у более свежей ambient. Небюджетно
  гарантирован только прямой адрес; у ответа-в-треде приоритет ВНУТРИ бюджета, а не
  абсолютный.

Ядро чистое и детерминированное (`now` инъектится, без I/O, без rng): вердикт
пиннится юнит-тестами и закалён мутационным тестированием — тот же принцип «LLM
вербализует → чистое ядро решает», что и `staleness.decide_staleness`. Семантику
(`salience`, флаги адресности) вербализует вышестоящий слой; ядро её только взвешивает.
`BacklogScorer` — фрозен-фасад без состояния, делегирующий в module-level `score` и
`select_catchup` (чтобы мутационной поверхностью оставались чистые функции).

**Прикладной шов и тон входа.** Use-case `CatchUp`
(`application/usecases/catch_up.py`) — это «догоняй по-человечески» как ОДНО
решение. `to_backlog_message` проецирует рантаймовый `MessageReceived` на доменный
`BacklogMessage` на прикладном шве, который знает user-id Боба (прямой адрес =
@упоминание или reply на реплику Боба; `at` и `salience` подаёт вызывающая сторона,
т.к. `MessageReceived` их не несёт), поэтому доменный `catchup.py` свободен от
импорта `MessageReceived`. `CatchUp.plan` за флагом OFF по умолчанию возвращает
`CatchUpOutcome.empty()` (Боб как раньше, без догоняющего); включённый — один проход
`select_catchup` плюс тон входа `absence_hint` из `personality/absence.py` (та же
текстура «давно не виделись», что уже использует reply-tier; `None` при коротком
гэпе или пустом last-seen). Бэклог — это тот же недренирующий снимок
`ChatInbox.peek_since` (буфер приёма из среза 2.1), большим окном, второй буфер не
строится.

**Провязка live за флагом `presence.catchup.enabled` (BOB-066 Срез W.3).** Живая
re-entry-врезка вшита в per-chat воркер `ChatDispatcher`: коллаборатор `CatchUpReentry`
(`application/runtime/catch_up_reentry.py`) через чистый гейт-гэп `presence.catchup.is_reentry`
проверяет паузу отсутствия (`absence_hours`, по умолчанию 4.0), и на входе после
отсутствия делает ОДИН проход `select_catchup` над батчем (фокус + бюджет отвечены,
ambient просмотрен и осел без idle-утечки), возвращая `CatchUpSelection`. Флаг
`presence.catchup.enabled` OFF по умолчанию → `catch_up_reentry` не строится, воркер как
раньше. Knobs — `presence.catchup.{absence_hours,budget}` (по умолчанию 4.0 ч / 3).

### P0-упрощение адаптера (честно)

В `episodic_log` пока НЕТ колонки `chat_id` (модель данных BOB-066 её не добавляет —
в P0 у Боба один активный чат), поэтому `EpisodicOutgoingActivityStore` принимает
`chat_id` ради контракта порта и форсайта BobNet, но окно считает над всем недавним
потоком. Когда будущая миграция сегментирует эпизоды по чату, сюда без изменений
домена добавится `WHERE chat_id = ?`.

### Форсайт BobNet

Окно участник-агностично: реплика человека и реплика Боба-копии считаются одинаково.
Потолок доли эфира применяется к ЛЮБОМУ ambient-участнику, включая ботов, — тот же
субстрат работает в топике BobNet без переделки ядра.

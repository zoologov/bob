# BRIEF — BOB-111: способность честно объявляет себя недоступной

> **Тип:** feature · **Приоритет:** P1 · **Беада:** `bob-zbc` · **Issues:** #62 (остаток)
> **Ветка:** `features/BOB-111` · **Заведено:** 2026-08-19

---

## Проблема

Боб узнаёт, что онемел, **в момент, когда его спросили**. При переезде на VPS (BOB-094) у него
молча отвалились две способности сразу — интроспекция (нет `beadloom`) и рендерер (`mmdc_bin`
указывал на путь с макбука владельца). Обе прожили так до 18 августа, когда владелец попросил
схему и получил выдумку и пустоту (BOB-110).

Между «способность сломана» и «мы об этом узнали» стояло **живое сообщение в группе**. Это и есть
остаток Issues #62: у способности с внешним инструментом нет проверки доступности при старте.

## Что именно проверять

Внешних бинарей пять, и каждый гасит понятную способность:

| Инструмент | Что перестаёт работать | Где настраивается |
|---|---|---|
| `beadloom` | схема архитектуры, влияние, состояние проекта | `capabilities.introspection.beadloom_bin` |
| `bd` | разговор о задачах трекера | `…bd_bin` |
| `git` | разговор об истории репозитория | `…git_bin` |
| `mmdc` | картинка из mermaid | `diagrams.mmdc_bin` |
| `claude` | Боб-кодер | `coder.claude_bin` |

## 🔴 Проверка судит ДОСТИЖИМОСТЬ, а не текст конфига

Это прямое требование §0.3 п.12, и здесь оно не теоретическое: сломавший нас `mmdc_bin` был
**синтаксически безупречен** — валидный абсолютный путь, заданный осознанно, с объяснением рядом.
Любая проверка «по форме строки» его бы пропустила. Не пропускает только вопрос «а он вообще
запускается на ЭТОЙ машине?».

Отсюда правила разрешения:

- **голое имя** (`beadloom`) — ищется по `PATH` того процесса, что будет его звать;
- **путь** (`/Users/…/mmdc`) — проверяется на существование **и** исполняемость.

Путь с чужой машины проваливает второе. Именно так ловится класс #48/#62.

## Решение

**1. Чистое доменное ядро** `capabilities/tool_availability.py`: по списку требований и функции
разрешения выносит вердикт на каждое — доступно или нет, и **почему**. Детерминированное,
без I/O, пригодное для mutation-гейта (§0.2).

**2. Разрешение как отдельный шов** (adapter): `PATH`-поиск и проверка исполняемости — реальный
контакт с файловой системой, вынесенный из ядра.

**3. Видимость при старте.** Недоступность называется **явно**: способность, инструмент, причина.
Не «warning где-то в логе», а строка, которую нельзя прочитать как «всё хорошо» — по образцу
`-rs` у pytest и аннотации `config-check` в CI (BOB-108): у отключённого должно быть видимое
состояние, а не тишина.

### Чего работа НЕ делает (честная граница)

- **Не мешает Бобу жить.** Отсутствие `mmdc` не должно ронять старт: Боб продолжает работать без
  картинок. Отказ стартовать был бы хуже болезни.
- **Не чинит недоступность.** Установка инструментов — дело выкатки (BOB-110); здесь только
  честное знание о своём состоянии.
- **Не обещает, что Боб сам расскажет владельцу.** Пока — видимое состояние при старте. Реплика
  в чат — отдельное решение, и обещать её в этой работе значило бы обещать больше, чем сделано.

## Проверка (двойной прогон, §0.3 п.12)

- **Саботаж «путь с чужой машины»** (`/Users/…/mmdc` на linux): новый гард краснеет, старого
  гарда не существовало — поэтому сравнение идёт с **поведением до фикса** (тишина).
- **Саботаж «инструмент исчез с PATH»**: вердикт становится «недоступен» с названной причиной.
- **Ловушка на вакуумность:** пустой список требований не должен читаться как «всё доступно» —
  проверяется отдельно, иначе гейт зелен при нулевой работе (§0.3 п.6).
- **Mutation** на ядре ≥85% с разбором эквивалентных мутантов.

## Приёмка

- [ ] Ядро выносит вердикт по каждому требованию, с причиной
- [ ] Путь с чужой машины распознаётся как недоступный
- [ ] Голое имя резолвится по `PATH`
- [ ] При старте недоступность видна явно (способность + инструмент + причина)
- [ ] Отсутствие инструмента НЕ роняет старт
- [ ] mutation ≥85% на ядре, число мутантов названо
- [ ] Двойной прогон

# BRIEF: BOB-103 — лог без ротации + опрос без бэкоффа

> **Status:** Approved
> **Created:** 2026-08-18
> **Bead:** `bob-3rk` (`type: bug`, P2)

---

## Проблема

Найдено координатором при проверке здоровья живого процесса (не по жалобе).

**1. Лог растёт без предела.** `logs/bob.log` = 2.7 ГБ, ведётся с 2 июля, ротации нет.
~13 млн строк с error/traceback — как инструмент диагностики лог мёртв.

**2. Опрос без бэкоффа = хот-луп на обрыве сети.** Корень измерен по коду:
- поллинг крутится `periodic(poll, interval_seconds=0.0)` (`runtime/wiring/proactivity.py`):
  при живой сети это правильно — `get_updates` держит long-poll до `poll_timeout` и сам
  задаёт темп;
- но при обрыве `get_updates` бросает `ServerDisconnectedError` МГНОВЕННО, `_poll_bot`
  (`infrastructure/telegram/multibot.py`) ловит и `return 0` — неотличимо от «нет
  обновлений», — и цикл с интервалом 0 бьёт снова сразу. Отсюда ~30 тыс. строк «poll
  failed» в сутки на бота (замерено: ~каждые 3 сек), лишний CPU и батарея на ноуте.

## Решение

### Часть 1 — бэкофф на сбое опроса (главное)

- Опрос РАЗЛИЧАЕТ исход: успех (в т.ч. «0 обновлений») vs сетевой сбой. Сейчас оба дают `0`.
- На сбое — пауза, растущая с числом ПОДРЯД идущих сбоев (экспонента с потолком). Чистое
  ядро `next_backoff(consecutive_failures) -> seconds` — детерминированное, mutation-цель.
- 🔴 **Лечение не должно быть хуже болезни.** Первый УСПЕШНЫЙ опрос сбрасывает счётчик в 0 —
  значит после возврата сети доставка НЕ ждёт максимальной паузы. Потолок скромный (напр.
  ≤30 с), чтобы восстановление было быстрым. Это ПРОВЕРЯЕТСЯ отдельным тестом:
  сеть вернулась → первый успешный опрос происходит быстро, а не через потолок.
- При живой сети (long-poll) поведение БАЙТ-В-БАЙТ прежнее: бэкофф только на сбойном пути.

### Часть 2 — схлопывание повторов в логе

Повторные ОДИНАКОВЫЕ «poll failed» не сыпать строкой на попытку: логировать первый, потом
«повторилось N раз за M» (или ронять до DEBUG после первого, WARNING на смену состояния).
Бэкофф и так снизит частоту; это добивает шум.

### Часть 3 — ротация лога, независимая от хоста

🔴 Сейчас лог пишет НЕ Python, а shell-редирект лаунчера (`./bob`: `>> logs/bob.log 2>&1`);
`runtime/main.py::_configure_logging` — `basicConfig` в stderr. Поэтому `RotatingFileHandler`
сам по себе НЕ поможет, пока лаунчер дублирует в тот же файл.
- Приложение берёт владение логом: `_configure_logging` ставит `RotatingFileHandler`
  (`maxBytes` + `backupCount`, значения из `runtime.log_*`), файл — `logs/bob.log`.
- Лаунчер `./bob` перестаёт редиректить stdout/stderr в ТОТ ЖЕ файл (иначе двойная запись
  и гонка с ротацией): редирект в отдельный маленький bootstrap-лог или в /dev/null, а
  рабочий лог владеет приложение.
- 🔴 Это заодно ПРАВИЛЬНО для BOB-094 (VPS): ротация не должна зависеть от того, кто
  запустил процесс (systemd/journald на VPS не будет знать про shell-редирект).

## Границы

- `2.7 ГБ`-файл руками не трогаю в этой работе (у owner'а может быть нужда в истории);
  ротация начинает действовать со следующего цикла. Отдельно предложу owner'у усечь старый.
- Не меняю семантику приёма (offset/poison-cap BOB-070) — только ПАУЗУ между сбойными
  опросами и то, КАК пишется лог.

## Критерии приёмки

- [ ] Хот-луп воспроизведён (сеть-вниз симулирована) и показано, что частота попыток ПАДАЕТ
- [ ] 🔴 После возврата сети первый успешный опрос — быстрый (тест на «лечение не хуже болезни»)
- [ ] Живая сеть: путь опроса байт-в-байт прежний (бэкофф только на сбое)
- [ ] `next_backoff` — чистое ядро под mutation (≥85%, число мутантов названо)
- [ ] Повторные одинаковые сбои не сыпят строкой на попытку
- [ ] Лог реально ротируется по размеру; лаунчер не дублирует запись (проверено)
- [ ] `beadloom ci` зелёный

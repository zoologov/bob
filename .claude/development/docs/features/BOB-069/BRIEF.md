# BRIEF — Адресность мид-вокатив + утечка tool-call в чат

## Проблема (две живые, найдены owner в топике Боба)

Обе грубо нарушают north star «никогда не выглядеть программно».

### A. Вокатив «Боб» в середине фразы не распознаётся как обращение
«**Боб**, ты тут?» (в начале) → отвечает сразу. «Кстати, **Боб**, расскажи…» (в середине) → **молчит**.
Корень: `_is_name_address_to_bob` (`src/bob/conversation/addressivity.py:121-137`) детектит вокатив
только через `startswith(name)` после `lstrip` — имя обязано ЛИДИРОВАТЬ. «Кстати, Боб,» начинается
с «кстати» → `False` → `AMBIENT` → reflective-судья → IGNORE. Суффикс-guard (`rest[:1] in
_ADDRESS_SEPARATORS`) правильно отсекает «Бобу»/«Боб молодец» — его СОХРАНИТЬ.

### B. Tool-call протёк в чат текстом вместо выполнения
На «расскажи про BDD… на примере файла из tests/acceptance/features/» ответ в БД =
`[tool_calls] read_code({"query": "..."})` — сырой вызов текстом. Корень: `_assistant_turn`
(`src/bob/capabilities/usecases/tool_loop.py:110-117`) реконструирует assistant-ход, зашивая
tool-интент СТРОКОЙ в `content` (`f"[tool_calls] {rendered}"`) БЕЗ структурного поля `tool_calls`.
Re-ask (turn 2) малформ по OpenAI-схеме → Qwen (`disable_thinking:true`) эхом повторяет строку →
`_fallback_tool_call` (`openai_compat.py:196-300`) её не распознаёт → строка уходит как reply.

## Решение

### A — расширить чистую функцию `_is_name_address_to_bob`
Детектить вокатив «Боб» в ЛЮБОЙ позиции: имя с границей слова слева (начало ИЛИ разделитель/пробел:
«, Боб», «эй Боб») и разделителем-обращением/«!»/концом-строки справа. Добавить «!» в терминаторы
(«Боб!» сейчас тоже не ловится). 🔴 СОХРАНИТЬ суффикс-guard: «Бобу…», «Боба…», «Боб молодец» (после
имени НЕ разделитель) → остаются AMBIENT. Пример allow: «Кстати, Боб, …», «…, Боб?», «эй Боб!».
Пример deny: «Боб молодец», «расскажу Бобу», «про Боба».

### B — сомкнуть петлю инструментов + страховка
1. **Структурный assistant-ход** (`tool_loop.py:_assistant_turn`): вместо `content="[tool_calls] …"`
   собирать `{"role":"assistant","tool_calls":[{"id","type":"function","function":{"name","arguments"}}]}`
   (arguments — JSON-строка), согласовать `tool_call_id` с `_run_tool` (`call.id`). Тогда re-ask корректен,
   модель связывает `tool`-результат с вызовом и доводит до финального текста.
2. **Защита-в-глубину** (`openai_compat.py` `_fallback_tool_call`/`_extract_tool_call_result`):
   распознавать текстовую форму (`[tool_calls] name({...})` и/или hermes `<tool_call>…`) как tool_calls;
   как минимум — НИКОГДА не отдавать наружу reply, начинающийся с `[tool_calls] ` (санитайз/повтор).
3. 🔴 **Живой смоук против реального Qwen MaaS**: прогнать tool-loop с реальным `read_code` и убедиться,
   что петля смыкается в текст, а не эхо. Если Qwen с `enable_thinking:false` не принимает
   `assistant.tool_calls` в истории — опереться на страховку (2) и/или включать thinking для tool-loop-тёрнов.

## Критерии приёмки
- «Кстати, Боб, …» → Боб отвечает; «Боб молодец»/«расскажу Бобу» → НЕ триггерит (не регресс).
- Запрос с инструментом → Боб ВЫПОЛНЯЕТ его и даёт нормальный текст; строка `[tool_calls]` НИКОГДА не в чате.
- pytest/mypy --strict/ruff/beadloom ci зелёные; mutation ≥85% на обоих чистых ядрах; живой смоук tool-loop ОК.

# RFC: BOB-094 — переезд на VPS

## Целевая среда

Ubuntu/Debian (apt), systemd. VPS x4/8ГБ/90ГБ, только исходящие соединения (Telegram long-poll +
Qwen MaaS). Отдельный системный пользователь `bob` — не owner.

## Артефакты (в репозитории, каталог `deploy/`)

### `deploy/bob.service` — systemd-юнит

```
[Unit] After=network-online.target; Wants=network-online.target
[Service]
User=bob  Group=bob
WorkingDirectory=/opt/bob            # ДОМ Боба, НЕ репозиторий owner'а
EnvironmentFile=/opt/bob/.env        # секреты, права 600 bob:bob
ExecStart=/opt/bob/.venv/bin/python -c "<тот же вход, что ./bob>"
Restart=on-failure  RestartSec=5
[Install] WantedBy=multi-user.target # автозапуск при перезагрузке
```

🔴 `User=bob` — структурная граница BOB-093: процесс не под owner'ом, ssh-дорога (`~` по passwd)
и локальный файловый путь к репозиторию owner'а физически недостижимы — их просто нет у `bob`.

### `deploy/bootstrap.sh` — идемпотентная установка

Шаги (каждый проверяет, не сделан ли уже): `useradd -r -m -d /opt/bob bob`; apt-пакеты (python3.12,
git, curl); установить `uv` и `bd`; `uv sync` в `/opt/bob`; создать `data/`, `logs/`; положить юнит,
`systemctl daemon-reload`. 🔴 Секреты НЕ трогает — `.env` кладёт owner отдельно (runbook). Прогон
дважды подряд не ломается.

### `deploy/backup.sh` + `deploy/bob-backup.timer` — бэкап `data/`

`sqlite3 bob.db ".backup"` (консистентно, не cp на живой БД) в `/opt/bob/backups/`, ротация по
числу. systemd-timer раз в сутки. Восстановление — `.restore`, проверить на копии.

### `.github/workflows/deploy-bob.yml` — автодеплой (CD)

Триггер (решение owner'а): **push тега `v*` / GitHub Release** (+ `workflow_dispatch` руками). НЕ на
каждый мёрж — значит выкатка/рестарт живого Боба идёт осознанным релизом, а рутинные мёржи в `main`
Боба не трогают. Шаги: SSH на VPS ключом из секрета → `git fetch && git checkout <tag>` в `/opt/bob`
→ `uv sync` → материализовать `/opt/bob/.env` из GitHub Secrets (права 600) → `systemctl restart bob`.
🔴 До рестарта — быстрый гейт (`ruff`/`mypy`/узкий `pytest`), чтобы «задеплоил сломанное» не стало
новым классом (CI по PR — BOB-095, отдельно). Секреты из `secrets.*`, в лог НЕ печатаются (маскируются
GitHub'ом). Кто ставит тег: owner или координатор, когда батч работы готов к выкатке.

**GitHub Secrets** (owner заводит, значения через меня не проходят): `BOB_VPS_HOST`, `BOB_VPS_USER`,
`BOB_VPS_SSH_KEY` (для деплоя), `BOB_LLM__TIER1_API_KEY`, `BOB_LLM__TIER0_API_KEY`,
`BOB_TELEGRAM__TOKEN`, `GUPPI_TELEGRAM__TOKEN`. Workflow собирает из них `.env` на VPS.

### `deploy/RUNBOOK.md` — ПЕРВИЧНАЯ установка (один раз, руками owner'а)

(1) `bootstrap.sh` на VPS; (2) owner заводит GitHub Secrets (ключи, токены, VPS SSH-ключ);
(3) owner переносит свежий `data/bob.db` (`scp`, значения через owner); (4) остановить Боба на ноуте
(`./bob stop` — чтобы БД не разъехалась); (5) `systemctl enable --now bob`; (6) проверить ответ.
Дальше — **выкатки автоматические** через workflow, руками ничего.
Откат: `systemctl stop bob` на VPS, поднять на ноуте.

## Код: человечное объявление рестарта (BOB-090.D)

🔴 Голос Боба, не строка деплой-скрипта. Механика:
- **Перед остановкой.** `systemctl restart` шлёт SIGTERM. В graceful-shutdown Боба (`app.shutdown`,
  ДО закрытия транспорта) — послать owner'у/в группу живую реплику «обновляюсь, скоро вернусь». Это
  и есть предупреждение о рестарте. Окно короткое: одна отправка, с таймаутом, чтобы не задержать
  завершение (если сеть легла — молча выходим, шатдаун не блокируем).
- **После старта.** На старте, если предыдущий выход был апдейт-остановкой (маркер в `kv`/файле,
  выставленный shutdown-хуком), — реплика «вернулся, обновился». Если упал сам (не апдейт) — не
  притворяться апдейтом.
- **Формулировки — чистое ядро** `restart_voice(kind)` (уходит/вернулся) с несколькими живыми
  вариантами, mutation-цель, БЕЗ скриптованности (образец — `rule_voice` BOB-096). Саботаж: пустой/
  дефолтный голос → тест красный.

🔴 Кому объявлять (решение owner'а 2026-08-18): **owner-DM И группа**. Реже, чем казалось —
деплой по тегу, не на мёрж, так что группа видит объявление на осознанный релиз, а не на каждую
правку. Канал через существующий notifier Боба (его бот).

## Код: наблюдаемость «я оглох»

BOB-103 уже считает `_poll_failures[identity]` (подряд идущие сбои, сброс на успех). Надстройка:
чистое ядро `outage_state(consecutive_failures, threshold) -> bool` (mutation-цель) — «оглох», когда
сбоев ≥ порога. 🔴 Единичный блип — НЕ «оглох» (порог > 1). При переходе в «оглох» — WARNING-диагноз
ровно раз; при восстановлении — снятие ровно раз (не спамить). Порог из `telegram.outage_threshold`.

Доступ owner'а к сигналу: строка в логе (уже ротируется) + отражение в `./bob status` (или его
VPS-аналоге `systemctl status` + grep). Полноценный алерт в Telegram — 🔴 сознательно ОТДЕЛЬНО (Боб,
который «оглох», не может сам о себе написать — нужен внешний канал; назвать это ограничением, не
делать полу-решение).

## Дублёр на VPS

`coder`/understudy-флаги в конфиге VPS — БЕЗ локального Ollama (`tier0_fallback` не задан). При
отвале Tier-1 rescue-путь честно молчит. На ноуте дублёр остаётся ON (GPU есть) — гасим только в
конфиге VPS при переезде (решение owner'а).

## Что НЕ делаем

- Не Docker/k8s — один процесс + systemd.
- Не Postgres — SQLite файлом.
- Не автоматический cutover — секреты и запуск за owner'ом.
- Не Telegram-алерт «оглох» в этой работе — нужен внешний канал, отдельно.

## Риски

| Риск | Ответ |
|---|---|
| claude code на VPS из Индии не работает | owner проверял ранее — работает; runbook требует smoke до cutover |
| БД разъедется (пишут обе машины) | cutover ОСТАНАВЛИВАЕТ ноут перед финальным переносом bob.db |
| `.env` утечёт при переносе | переносит owner напрямую (scp), права 600; агент не касается |
| «оглох» даёт ложную тревогу | порог > 1, сброс на первом успехе (ядро под mutation) |
| bootstrap не идемпотентен | каждый шаг проверяет состояние; прогон дважды в CI-подобной проверке |

## Гейты

`ruff`/`mypy` на коде наблюдаемости; mutation на `outage_state`; BDD не требуется (ops-артефакты +
узкое ядро). `bash -n` на скриптах. Живой смоук самого VPS — у owner'а по runbook (сеть/машина).
